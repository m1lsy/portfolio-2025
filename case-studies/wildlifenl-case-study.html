WildlifeNL:
WildGids & WildRapport

Role

UX/UI Designer & Front-End Developer

Timeline

February – June 2026 · Internship

Tools

Figma, Flutter, Dart, Git, GitHub

Overview

During my internship at inMotionVR / GAMR, I worked on WildlifeNL, a project with two related mobile applications: WildGids and WildRapport. My role focused on UX/UI design and front-end development. I worked on making the apps easier to understand and use, while also implementing interface changes in Flutter.

The work involved more than adding new screens. I had to understand the existing apps, identify places where the experience could be clearer, and balance design improvements with the structure and technical requirements of an existing codebase. I collaborated with the development team and used feedback from the project stakeholders to guide decisions.

My focus

  • Reviewing and improving existing app interfaces and navigation
  • Designing clear flows for wildlife observations and incident reports
  • Translating UI decisions into Flutter components and screens
  • Working with Git branches to keep development tasks organised
  • Iterating on the interface while considering stakeholder feedback and technical constraints

The Challenge

Working with existing products

Both apps already had their own purpose and structure, so the challenge was to improve the experience without treating them as completely new products. I needed to understand how people would move through the apps, which actions should be easy to find, and how the different reporting tasks should be presented.

For me, this meant looking at the experience from both a design and implementation perspective. A layout could look good in Figma, but it also needed to work within the existing Flutter project and make sense alongside the other screens.

How can I make the main actions in WildGids and WildRapport easier to find and use, while keeping the interface consistent with the existing products?

Understanding the Apps

WildGids: start with the map

For WildGids, I focused on making the map central to the experience. The map is a natural starting point for exploring wildlife and observations, so the navigation should support that behaviour rather than make users search for the main content.

  • Prioritising the map as the main entry point
  • Making the observation action easier to discover
  • Thinking about how users move between exploring and recording information

WildRapport: make reporting easier to understand

WildRapport supports different types of reports. I worked with the structure around the main reporting categories and their place in the overall navigation.

  • Waarneming: recording a wildlife observation
  • Schademelding: reporting damage
  • Dieraanrijding: reporting an animal collision

These are different tasks, so the interface needs to help users recognise which report they should create and understand where to go next.

Design Decisions

Navigation and information hierarchy

One recurring consideration was how quickly users could find the action they needed. In WildGids, I wanted the map to feel like the main destination and the observation flow to be easy to access. In WildRapport, the different report types needed to be understandable within the app's broader structure.

Consistency without forcing both apps to be identical

WildGids and WildRapport serve different purposes, so the goal was not to make every screen the same. Instead, I considered how shared patterns, clear labels and a consistent visual language could make the products feel related while still supporting their different tasks.

Design within technical constraints

Because I was also implementing the interface, I could consider how a design would translate into Flutter. This helped connect the visual decisions with the real app structure and made it easier to spot when a proposed change needed to be adjusted during implementation.

Implementation

Flutter front-end development

I worked in the existing Flutter codebase, using Dart to implement interface changes. The project also used packages such as flutter_map, geolocator, shared_preferences, flutter_svg and package_info_plus.

My focus was on the front-end experience and how the screens and interactions worked together. I collaborated with the wider team rather than treating the apps as standalone builds.

Version control and collaboration

Git and GitHub were part of my day-to-day workflow. I used feature branches to separate areas of work, including styling and individual reporting flows. This made it easier to work on a specific task while keeping the work organised for integration.

  • styling/ui-polish — interface styling and refinement
  • feature/waarneming-flow — observation flow
  • feature/schademelding-flow — damage-reporting flow
  • feature/dieraanrijding — animal-collision reporting

The backend work was handled separately in collaboration with Guus. Coordinating the front-end and backend work helped me understand the importance of clear ownership, branch organisation and communication within a shared codebase.

Reflection & Learning

This internship gave me experience working on existing products where design and development decisions are connected. I had to understand the current experience before proposing changes, and then consider how those changes would work within a real Flutter codebase.

  • Designing for an existing product: learning to improve an established interface instead of starting with a blank canvas.
  • Connecting UX and implementation: considering both the user experience and the practical details of building screens in Flutter.
  • Working collaboratively: coordinating front-end work with backend development and responding to stakeholder input.
  • Making design decisions: explaining the reason for a change and balancing usability, consistency and technical constraints.
  • Using version control: organising work through feature branches and collaborating within an existing development workflow.
The biggest lesson was that improving an app is not only about making individual screens look better. The navigation, the task flow, the implementation and the people involved all shape the final experience.
